# Generic System Analysis + Deep Research v3 — Optional Appendices

These modules are **not part of the default Core execution path**. Use them only when their specific function is needed.

## Appendix A — Late Challenge / Completeness Checklist

**Use only after empirical Phase A and initial problem clustering.**  
Do not use this list to generate the first findings.

Challenge the analysis for possible missed classes such as:

- under- or over-formalization;
- mismatch between user need and system representation;
- local optimization versus end-to-end value;
- coordination / handoff burden;
- hidden or transferred cognitive work;
- missing or excessive governance/control;
- state/provenance loss or duplicated truth;
- premature or insufficient generalization;
- architecture/tool choice driving the problem framing;
- automation overreach or underuse;
- proxy/test success diverging from real utility;
- missing recovery / observability / feedback;
- data quality, reliability, security, rights or operational fragility;
- insufficient domain quality or insufficient structure.

For each candidate ask only:
1. Is it actually supported by project evidence?
2. Is there a stronger alternative explanation?
3. Is the opposite problem equally plausible?
4. Would the finding matter to the Research Agenda?

Unsupported checklist items are discarded.

## Appendix B — Disciplinary Discovery Map

Use only as a search-vocabulary aid when a problem cluster needs additional theoretical or methodological homes.

Possible areas include:

- domain-specific scholarship and professional methods;
- Requirements Engineering / software engineering / architecture / empirical SE;
- HCI / human-centred design / information behaviour / sensemaking;
- CSCW / coordination / organizational studies / distributed cognition;
- safety / resilience / incident and error research;
- epistemology / sociology and philosophy of science / interdisciplinarity;
- knowledge management / information systems / research infrastructures;
- data/provenance/reproducibility / research software engineering;
- human-AI interaction / AI-assisted work / automation studies.

This is not a required field list. Add, split or ignore fields according to the observed problem.

## Appendix C — Multi-Repository Extension

Use only when multiple cases are genuinely in scope.

1. Analyse each repository independently through Phase A and its own Research Agenda.
2. Do not infer genericity from shared vocabulary alone.
3. Compare mechanisms only after case-local findings are established.
4. Classify cross-case patterns as:
   `case-specific | domain-specific | tool-specific | organization-specific | AI-interaction-specific | cross-case recurring | potentially generic | unresolved`.
5. Seek countercases where similar conditions did **not** produce the same phenomenon.
6. Preserve different causal explanations if the evidence does not justify unification.
