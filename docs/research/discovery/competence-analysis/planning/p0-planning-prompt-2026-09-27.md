# 11. Gap Contract

Erstelle eine explizite Gap-Taxonomie für diesen Run.

Für jede Gap-Art festhalten:

- Definition;
- Beispiel aus diesem Arbeitsstrang;
- wer sie schließen kann;
- welche Evidence zur Schließung nötig ist;
- was KEINE Closure darstellt;
- welcher Status nach diesem Sicherungslauf erwartet wird.

Mindestens prüfen:

### Persistence Gap
Ist der materielle Analysebestand außerhalb des Chats restartbar gesichert?

### Analysis Representation Gap
Ist der bestätigte Analysebestand vollständig und semantisch korrekt repräsentiert?

### Knowledge / Erkenntnis Gap
Welche historischen/fachmethodischen Fragen sind noch ungeklärt?

### Profile-Boundary Gap
Welche Kompetenzen könnten nach SOTA split/merge/reframe werden?

### Domain-SOTA Gap
Welche Methodenliteratur/Standards/Forschungstraditionen fehlen?

### Method-Validation Gap
Welche positiven, adversarialen, evidence-starved und Cross-Case-Prüfungen fehlen?

### Understanding/Judgement Gap
Welche Bedeutung/Entscheidung müsste ggf. noch vom Owner oder qualifizierten Fachreview bestätigt werden?

### System/Capability Gap
Welche technische/systemische Fähigkeit fehlt tatsächlich – falls überhaupt?

Harte Regel:

Dokumentexistenz darf niemals automatisch einen Knowledge-, Method- oder Capability-Gap schließen.

# 24. Automatisierung / technische Ausführbarkeit

Der Owner wünscht:

> innerhalb des Blocks soll der jeweils nächste Worker nach PASS weitgehend automatisch angeschoben werden; nur echte STOPs sollen zurück in den starken Steering-Kontext führen.

Prüfe CAPABILITY-FIRST, ohne Produktfunktionalität zu erfinden:

1. Kann die verfügbare Umgebung tatsächlich programmgesteuert isolierte Work-Chats / Jobs erzeugen?
2. Kann sie Modell-/Reasoning-Klassen festlegen?
3. Kann sie Ergebnisse eines Workers persistent als nächsten Input bereitstellen?
4. Kann sie Transitionen automatisiert auswerten?
5. Kann sie frische unabhängige Kontexte garantieren?
6. Welche Schritte benötigen eventuell weiterhin einen manuellen Startklick?
7. Welche Teile sind trotzdem deterministisch vorgeplant, sodass der Mensch nur Transport und keine fachliche Workflowarbeit übernimmt?

Streng unterscheiden:

A. semantisch automatisierbar;
B. technisch aktuell automatisierbar;
C. vorbereitet, aber manuell zu transportieren;
D. nicht automatisierbar wegen Authority/Judgement.

Keine ungesicherte Behauptung vollständiger technischer Autonomie.

Entwirf einen Fallback:

Wenn automatische Worker-Erzeugung nicht verfügbar ist, muss das Repo trotzdem so vollständig sein, dass:

`next packet` deterministisch feststeht
und ein manueller Start keine neue fachliche Planung erfordert.
